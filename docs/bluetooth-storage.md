# Bluetooth profiles owned by server ID

Wi-Fi remains a readable attribute of each configured server. Bluetooth state is generated by the system and stored
as an opaque runtime profile belonging to the same stable `server.id`. It is not a hand-authored address/key field.
Changing display names, list order, Wi-Fi passwords or importing an update with the same server ID preserves the profile.

## On-device layout

| NVS namespace | Contents |
| --- | --- |
| `mirtar` | Existing human-readable device/server/Wi-Fi configuration |
| `mi_<hash>` | One 55-byte binary profile header: format, SDK version, full server ID, local static identity, selected bank |
| `ma_<hash>` / `mb_<hash>` | Two generations of this server's opaque SDK bonding blobs, IRKs and CCCDs |
| `mtb_pending` | Fresh enrollment staging identity and bond blobs, promoted only after physical confirmation |
| old `nimble_bond` | Legacy shared data, retained and not automatically assigned or deleted |

The 48-bit namespace hash is an index, not authentication. Full IDs in headers detect collisions; mismatches fail closed.
The binary layout is versioned and tied to the current ESP-IDF 5.5.6 store ABI. Incompatible headers are rejected.
The SDK's existing NimBLE persistence functions are retained. A link-time `nvs_open` wrapper redirects only the literal
`nimble_bond` namespace to the selected profile bank; other NVS namespaces pass through unchanged. Selection occurs only
with the NimBLE host stopped. An unselected store cannot fall back to the old global namespace.

Each server has its own automatically generated random static badge identity. It is stable across reboot/reconnect,
distinct from the display name and selected before advertising. Windows receives the observed address type explicitly.
Consequently, different hosts do not reuse one global badge bond. No user needs to discover or edit Bluetooth MACs.

## Enrollment and reset

Add server starts with a fresh staging identity. After pairing and physical host confirmation, the staging blobs and
identity are copied into an inactive bank belonging to that server ID. Promotion requires one completed bonded peer;
an enrollment window containing multiple peers must be restarted rather than guessing ownership.
Its metadata pointer is then published as one NVS
blob. The normal connection reuses that identity and pairing. An interrupted/failed copy never publishes a partial bank.
The live enrollment link stays on staging until shutdown so its confirmation receipt can still be delivered.
Starting a new enrollment clears only staging, never another server's storage.

Reset requires physical confirmation and an exact match with the currently selected server ID. The host stops, the
selected server switches to an empty bank with a new static identity, and its previous bank is cleared. Other servers'
metadata, banks, identities and configuration are not touched. Windows discovers this host's new identity and requests
a fresh PIN; resetting all computers is not a fallback. Old Windows records can be removed manually if desired.

Older shared bonds cannot be safely attributed to server IDs, so they remain unused and unchanged. Each host pairs once
when upgrading to this storage design. Complete merged firmware flashing still replaces NVS; preserving NVS is a separate
flash operation and is not equivalent to the on-card per-server reset.

NVS is not encrypted. A/B generations protect profile publication, not secrecy or guaranteed behavior under arbitrary
flash faults. Physical persistence, available NVS space across four active hosts, radio reconnection and enrollment
acceptance still require hardware testing. Raw keys and snapshots must never be published.
